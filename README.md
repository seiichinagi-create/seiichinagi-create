### 週次追記（10月11日）— 今週は「検査される側」が変わった

先週までの査読は、主にプラグインを**ホストの中で**調べていた。今週は逆で、**ホストの側を検査対象にした**。

**1. 規格の審判を入れた結果、27本に共通の欠陥が出た。** Steinberg 公式の VST3 validator（SDK 3.8.1）を取得して全プラグインに回すと、29本中25本が同じ1件で落ちた。`Programlist 000->Program 000: has no name`。原因は `getProgramName` が空文字を返す**1行**で、同じ雛形から量産したため、欠陥も27リポジトリに複製されていた。直したのも1行で、再検査では26本が47件すべて合格した。量産の効率は、欠陥の複製効率でもある。今週の収穫は、その「複製された欠陥」を**規格側の物差しで一度に洗えた**ことだ。

**2. 「検査が噛むこと」を、検査の側に要求し始めた。** vst-testbench の固定リグは、遅延補償（PDC）の零差テスト（残差 −145 dB）を持つが、同時に**補償しなかった場合は零にならない**対照を必ず置く。遅延の実測にも、真値を自分で決めた偽の遅延装置を通し、正直な申告と嘘の申告を区別できることを示す。この対照が、**テスト装置自身の1サンプルのずれ**（真値7を8と測った）を最初に見つけた。検査が通ったことより、検査が落ちうることのほうを先に証明している。

**3. 見つかったものは、プラグインの外にあった。** 非同期のキャプチャ読み込みが描画と競合し、60回中4回だけ結果が違った。ホストのグラフが、プラグインの遅延申告より先に補償を決めると、40回中2回はドライ経路が**エラーなしで**補償されなかった。プラグインをレンダースレッドで破棄するとホストが落ちた。どれも「各部品は正しく、つなぎ方が間違っている」種類の不具合で、単体試験では見えない。さらに、PAGANIHANDS・Flesh808・Bass Cafeteria は、**2台同時に鳴らすと別々に鳴らした和にならない**（Matryoshka Guitar と Retrophie SN は −147 dB で一致する）。この一件は、まだ原因が分かっていない。

**4. AI から DAW を触らせる口は、許可リストで作った。** REAPER 用のブリッジは、任意のスクリプトを走らせる口を**意図的に持たない**。型付きの命令だけで、変更はすべて取り消し1手。ここでも落とし穴は「表示を信じたこと」だった。Ozone はパラメータの表示文字を設定の直後には更新しない。それを読み戻して探索したところ、出力上限が −10 dB に置かれていた。以後、**測った出力だけを見て探索する**。

**5. 耳が先に見つけた誤り。** キラキラ星のヘビーロック版は、数値上はすべて正常（ピーク・帯域・無音検出）だったが、聴いた作者に「斬新なコード進行」と言われた。旋律を見ずに1小節1コードで決めていたからだ。以後は、旋律の全音がそのときのコードの構成音かを**機械的に検査**してから作る。数値では見えない領域があることを、人の耳が教えた。

> **今週のまとめ一文**: 作者の検査は「プラグインが正しいか」から「それを動かすホストが約束を守るか」へ移り、同時に「検査そのものが外れる可能性」を先に示す形になった。

### 総評

旧版で私は、9月を「締め切りのある仕事を、現物から仕様を読んで間に合わせた月」と要約し、10月の追記を **「他人の現物を一次資料として読む」** と書いた。この要約は、その後の一週間で**もう一段進んだ**。しかも旧版そのものが、公開の約5時間後に作業指示として回収された（後述）。

9月末〜10月初めに入ったのは、**別のAIにレビューさせる**手法だ。ただし、AIに褒めてもらうためではない。10月1日〜4日の4日間だけで、少なくとも **9本のリポジトリ**（matryoshka-guitar、TUPLET、csvmini、3face-sampler、retrophie、ARM、kojutsu、SF2 Player、PTPCounter）に外部AIの査読が入り、その所見が**1件ずつ実測で仕分けられた**。そして6日・7日には、DroneWeaverが4つのAI（ローカル3機＋独立したClaude）とChatGPTに査読された。

旧版の言葉で言えば、こうなる。**他人の書類を一次資料として読んでいた作者が、今度は「AIの所見」を一次資料として読み始めた。** 所見は証言であって判決ではない。採るか捨てるかは、現物（コードと測定）が決める。この姿勢は、7月に作者が自分の道具へ要求した「反証可能性」を、**レビューという行為そのものにまで広げた**ものだ。

そして今月の批評の中心は、旧版と同じく「表札と中身の食い違い」だが、舞台が変わった。READMEではなく、**資料とコードのコメントと、査読者の頭の中**だ。

### カテゴリ1：「別AIに読ませる」の運用——褒めさせず、実測で仕分ける

この手法が単なる流行で終わっていない証拠は、**中身**にある。外部AIの査読を検証した記録から、実際に直った不具合を拾う。

- **3face-sampler**：補間の重みが逆転していた（説明書のkの記述も是正）
- **csvmini**：保存の失敗経路が2つ（失敗時に編集が消える／マッピングが欠ける）、見出し切替時の選択ずれ
- **retrophie**：伸ばした音のベンドとアタックの減衰、ベンチを新設
- **TUPLET**：幽霊和音（無料版のDeepSeekの査読を検証して根治）
- **ARM**：ドラムがほぼ無音だった
- **matryoshka-guitar**：外部レビュー5項目を実測で仕分けて4件を改修

運用の型も固まった。**①依頼文で褒め言葉を禁じ、弱点から探せと書く**（DroneWeaverの依頼文には「作者はこれを自信作だと言っている。その言葉に引きずられず」とある）。**②所見を現物で仕分ける**（採用／却下／保留）。**③却下の理由も、採用と同じ粒度で記録する**——retrophie の試験外見「CALM」は、試した上で不採用・取り消しになっている。

### カテゴリ2：査読者の欠陥という一次資料——DroneWeaverの7日間

最も読み応えがあるのは、10月6日〜7日の **vst-drone-weaver**の記録だ。ここで起きたことは、この手法の長所と限界を、一度に見せている。

**ローカルの3機（gpt-oss / gemma4 / qwen3）は、そろって dB の値を「%」と読んだ。** 設計の説明（「音色は数小節かけて滑る」）をそのまま信じて採点し、gemma4 は持続に9点を付け、qwen3 の指摘は互いに食い違った。和音の入れ替えを、楽器自身のゆらぎと取り違えた。

役に立ったのは、独立して走らせた Claude の査読と、それを**自分で検証した2点**だった。

> 音色モーフは「数小節」でなく約1秒だった（1歩0.00008＝時定数0.28秒。元のコードのコメントが誤り）。
> 3本の「ゆっくりしたLFO」は、実は約9秒周期で3本とも同じだった（目標を平均0.23秒ごとに引き直すため、レートが0.11Hzに収束）。

これは旧版が「表札と中身の食い違い」と呼んだものの、**コード内のコメント版**である。READMEの嘘ではなく、`// slow random-walk rate` というコメントが、数か月のあいだ実装と食い違っていた。それを見つけたのは、作者の耳でも、ローカルAIでもなく、**「コードから式を計算せよ」と命じられた査読**だった。

さらに翌日、ChatGPTのソース評価は、別の誤りを2つ生んだ。ChatGPT自身が PAD の立ち上がりを一次遅れと読み違え（実際は1サンプルずつ増える直線ランプで、全開まで0.19〜0.38秒）、**そして、私が書いた資料の「数秒のゆっくりしたアタック」が間違っていた**ことが、その再計算で露見した。査読者の誤りと、**依頼者（私）の資料の誤り**が、同じ式の確認の中で同時に見つかった。

ここから引き出せる規則は、旧版の「棚卸が正。自動値は入力であって答えではない」と同型だ。**AIの査読は入力であって答えではない。査読者の誤りも、一次資料として残す。**

### カテゴリ3：手法が道具になる——layerlab と、再現できる査読

新規の **layerlab**（レイヤー合成の小さな画像ツール、MCPサーバ付き、Rust）は、コミットの時刻が約40分に収まる速さで、エンジン→GUI→注釈→MCP→確認ツールまで積み上がった。最初のコミットの2分後にはREADMEがある。その最後のコミットが象徴的だ。

> Add review bundle generator and request template

**外部AIに読ませるための「資料の束」を作る生成器と、依頼文の雛形が、道具の機能として最初から入っている。** 手法が、作業習慣から**成果物の一部**に変わった。

DroneWeaver側にも同じ流れがある。`docs/ai_review/` には、依頼用の資料（dossier）、測定スクリプト、モデルに投げる実行スクリプト、そして**各AIの答えと、実測で確認した結果の要約**が、コミットされている。つまり「誰が何と言い、どれが当たり、どれが外れたか」を、後から再現できる。

ただし、ここに旧版から続く課題がある。**査読の記録が、まだ道具ごとにばらばらの場所にある。** 規則は配れても経路は道具ごとに新しく生まれる、という旧版の指摘は、査読にもそのまま当てはまる。

### カテゴリ4：音の側——AIに耳は無いので、最後は人の耳

音楽側は今月も、GitHubに映る範囲が窓の一部でしかないが、DroneWeaver の一週間は教訓が濃い。

3パート（BASS/PAD/TOP）の独立、音色モーフ、ARMのリズムエンジンの移植、非同期時のテンポのゆらぎ（約10分で±5%）、機械の負荷と時計から音列を作る自動演奏。どれも、**「耳のないAIが評価できる量」と「耳が要る量」を、依頼文の最後に分けて書かせる**形で進んだ。

象徴的なのは、人間の耳が下した2つの判定だ。自動演奏の最初の版（1小節に3〜5音）に対して、ユーザーは**「黄金コード進行のベタ打ちで萎えた」**と言った。AIの査読が褒めていたかどうかに関係なく、これは正しかった——1フレーズが1つの和音になり、和音解析が定番の進行に変えていたからだ。単音を間をあけて入れる形に直した。もう一つは、修正を重ねた版を聴いて、**「良いけど、前までとは別のドローンになってしまった」**。作者はそれを不具合として直さず、**VER1とVER2に分けて、両方をプラグインとして残した**。

AIの指摘は、耳の前では助言にすぎない。そして、**変えた後の音を変える前の音と並べて残す**という選択は、この手法の副産物として一番健全なものだった。

### カテゴリ5：宿題の採点と、新しい宿題

旧版で私は「来月ここが0本かつ新顔に説明文が付いていたら、習慣が治ったと書く」と約束した。採点は前掲のとおりで、名指しした分は片づいた。ただし新顔1本の話は断定しない。

新しい宿題を3つ置く。

1. **査読の独立性。** このレビューを書いている私は、DroneWeaver の査読で「独立した査読者」を務め、資料を作り、修正を実装し、その検証もした。**同じAIが、作者の手足であり、査読者であり、検証者である。** 手法の外側から見れば、この独立性は保たれていない。別系統のAI（ChatGPTなど）を継続的に混ぜているのは、その補償として正しい。
2. **査読の記録の置き場所。** 道具ごとにばらばらな「査読の記録」を、ハブの規約として一箇所に束ねること。
3. **「耳が要る」の台帳。** 毎回の査読の末尾にある「判断できないこと」を、**聴いたあとで決着した／していない**で台帳にすること。今のままでは、「聴いたらどうだったか」が資料に戻ってこない。

### 総括：このアカウントの本質（10月・改訂版）

6月「回路の物理を手で解き、AIの力を借りて音楽の意味を問い直している」。7月「作った道具に対して、反証可能性を要求し始めた」。8月「自分の労働を、道具に清算させはじめた」。9月「道具群を艦隊として運用し、属人性を外しはじめた」。10月の追記（旧版）「他人の現物を一次資料として読み、締め切りに間に合わせた」。そして改訂版の一文——

**「AIの所見を一次資料として読み、現物で仕分けるようになった。」**

課題は2つ。**第一に、査読の独立性**（上記）。**第二に、仕分けの規則が一人の注意に依存していること**——今月の仕分けが正確だったのは、毎回「式から計算せよ」「褒めるな」と依頼文に書き続けた注意のおかげで、配られた規則ではない。

今月の最注目は **vst-drone-weaver の7日間**——4つのAIの査読と、ChatGPTのソース評価と、耳の判定が1本の履歴に並んだ。今月のベストラインは、査読の結果を引いた次の一文だ。

> 「数秒のゆっくりしたアタック」と私が資料に書いたのは誤りで、実際は直線ランプの0.2〜0.8秒だった。

誤りを指摘された側の文として、これ以上に健全な一文は、あまり無い。
